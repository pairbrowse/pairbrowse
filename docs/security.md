# Security

PairBrowse drives a browser that is logged into your accounts, so it's built to keep that
browser to you and to Claude, and to limit what a malicious web page can talk Claude into.

| Risk | What PairBrowse does |
|------|----------------------|
| Another program or user on your computer takes over the logged-in browser | No remote-debugging port. Chrome is driven over a private pipe by the PairBrowse helper, and the only way in is a socket file in `~/.pairbrowse/run` that only your user account can open. Multiple trusted Claude Code sessions share a serialized queue and control leases; a call that holds the queue for more than 10 minutes is answered with an error and the browser is reset, so one stuck call can't keep every other session waiting. |
| The live view is reached by someone else | Starts with the browser, for its side panel. Listens on 127.0.0.1 only, on a random port (or your `liveViewPort`), behind a random 256-bit key in the URL. Join codes use a second 127.0.0.1 port (the only one the sharing tunnel reaches), where your key never works. Requests for any other host name are refused (stops DNS-rebinding), except the names you list in `liveViewHosts`, which take invite links only; input posted from other websites is refused too. The page sends no referrer, can't be framed, and runs only its own script and style files (a strict content security policy: no inline code or styles, nothing loaded from the web); those files come from a fixed list read at start, behind the same key. It stops when the browser closes. The side panel gets the address in memory at launch (extension session storage, never on disk), and the live view accepts its requests only from that extension's origin. |
| An invite link goes further than meant | Each invite has its own random 256-bit key, separate from yours, checked in constant time, and ends after 24 hours (7 days at most), when you revoke it, or when PairBrowse stops; expired and revoked keys get the same answer as a wrong one, and an open view ends at once. A watch link gets the page, tabs, activity and status only: the helper refuses its clicks, typing and tab changes. A drive link can also click, type and switch tabs, and only after you OK it (in Codex and other apps, Claude can't make one). Neither ever gets the Profile panel (remembered details, password names) or its updates, and a drive link can't open local-network addresses from the address bar. Drive input is accepted only from loopback or your `inviteBaseUrl` origin. Viewers other than you can't resize the page. Anyone with a drive link can still click and type in your logged-in browser. |
| A join code goes further than meant | A join code is a drive or watch invite (same key, roles, expiry and revocation) plus the address of a Cloudflare Quick Tunnel that reaches only the guest port. That address is one of the host's sharing connections: two such tunnels are kept up while codes are out (both to the same guest port, so a key works on either), every approved joiner learns the live addresses over their channel, and when one tunnel goes down a joiner already in moves to another on their own with the same key, without a new code or any change for them; the host starts a replacement, and `list` shows each unused code with a live address (its string may change). Only when every tunnel is gone for over a minute does the host hear, once, that sharing lost its connection. There, only join code keys work, only from PairBrowse (requests with a browser Origin are refused), and nothing (tabs, activity, state) is served until you approve that joiner, identified by a random id their PairBrowse makes: Allow in your own side panel or live view, in the join prompt in your tab (next row), or Claude's `approve`, which always asks you (other apps hand it to you); Claude hears your answer in its next result. Join codes, your yeses and their tunnels outlive a restart of PairBrowse (an update, a crash), so joiners reconnect without a new code: they're kept in `~/.pairbrowse/sharing.json` (readable by your account only; keys and joiners' names, nothing of your pages), and the next run takes over a tunnel only if its process is still PairBrowse's tunnel keeper for that same port (checked again before any signal, so a reused process id is never stopped). Each tunnel's keeper stops it once no PairBrowse helper has been running for 2 minutes, so a crash or a helper that never comes back leaves no public address forwarding to a port another account on this computer could take. A joiner's agent's results show no folder of this computer (accounts, temp and system folders, other disks): file names only. Your home and temp folders are hidden inside web addresses too (`https://site/?file=/Users/you/a.txt` crosses as `?file=~/a.txt`); web addresses are otherwise left whole. Closing the browser window, revoking or expiry end them (each joiner's channel, pictures and agent stop at once) and delete that file; invite links are never kept. **Remove** next to someone let in (owner's live view or side panel only, a real click) takes them out at once: their channel, pictures and agent stop, and that joiner id is refused from then on. Each approval is bound to one joiner id, which their PairBrowse makes anew for each join: someone turned away or removed who tries the same code again is a new request, and you're asked again (revoke the invite to stop that); at most 5 requests wait at once and new ones are rate-limited. An approved joiner keeps one WebSocket open (`<key>/events`, after the same key, approval and no-Origin checks; at most 2 per joiner, messages capped at about 200 KB, a heartbeat every second; Cloudflare's quick tunnels hold back streamed HTTP responses but pass WebSockets at once) and sends its changes on it, under the same limits as the plain requests that remain: tab changes (drive only, 3000 a minute), pointer positions (40 a second) and who-does-what and messages (4 a second, 20 KB each). With a follow code (mode "follow"), joiners never get a picture of your browser, favicons or the Profile, and nothing they send can click, press keys or submit in a page: see the next row. A shared browser code (mode "shared", the default) is different: see "Shared browser mode" below. The tunnel stops when the last code ends, on revoke_all and when you close the browser window. Cloudflare carries the traffic (TLS to Cloudflare). |
| A page or an agent answers a join request in the page or its notification | When someone asks to join, the host gets one alert at a time besides the side panel's list: while the browser window has the system's focus (read from the browser, by the side panel's worker: the last focused window is focused and not minimized; a page can't tell, as Playwright emulates focus for every page) and a web page is in front, the bottom bar of that tab (the side panel's worker names it) shows "Sam (Claude Code) wants to join (drive)", Allow, Deny, a close, at its right end for about 10 seconds, the newest request with "+N more"; otherwise a notification with Allow and Deny. Either comes down when the request is answered anywhere, revoked or expires; the request stays in the side panel. The bar's request is drawn inside its closed shadow root (no new element in the page, hidden from snapshots), and its text reaches the page script as data, never through the page's `JSON.parse`. A page can't click it (the buttons count only trusted pointer clicks, not keys or synthetic events), can't fake an answer (answers are kept inside the page script and read by the helper with the per-start key) and can't slip it under a click meant for something else: a click counts only 600 ms or more after what it shows last changed, and only while the browser reports it fully visible (IntersectionObserver v2: nothing drawn over it, no opacity, filter or transform; the bar drops its blur and doesn't fade while it asks). The helper checks again: the answer must come from the very tab the request was shown in, for a request still waiting, at least 600 ms after it showed, at a moment when no agent was acting (nor had acted in the second before) and no input was being replayed (a joiner's through their picture of the tab, or a live view viewer's, the owner's included: the live view has its own Allow). Only then is it answered the way the side panel's buttons answer it. A notification's buttons can only be pressed by the person (no page, agent or script can); the side panel's worker answers a press for the one request that notification was made for, the side panel's way (the live view's approve, with the owner's key it holds in memory), and the live view answers only a request still waiting. Clicking the notification itself only brings the browser to the front. Agents' clicks are real input too, which is why they never count; nor do the clicks of people already in the session. Limits: with the default driver the page script runs in a world of its own, out of the page's reach; with `browserDriver: "playwright"` it shares the page's world, where a hostile page could watch what PairBrowse draws (as for the badge and bar), still without clicking or answering it. A page can probe the bar by hit-testing and tell that something of PairBrowse's is there. People already in a shared browser session see the bar's request in the picture of your tab, and can't answer it. Without the side panel's worker the notification is the system's, text only (answer in the side panel). |
| Shared tabs carry more than addresses | With a follow code, joining shares tabs, not a screen: each side's own browser opens the other's tabs, and each person stays signed in as themselves (cookies, storage, passwords and remembered details never travel, and there is no screencast for joiners). Only http(s) addresses cross, in both directions, and never with `user:pass@`, for localhost, local-network or single-label hosts, or IPv6 literals (a dev server the host shares crosses under its own tunnel address, below); `file:`, `chrome:`, `data:` and `javascript:` never do. Watch joiners get origin and path; approved drive joiners also get the query string minus parameters named like credentials, codes, sessions or personal details and secret-looking values, and fragments only as `#/routes`. Tabs on the sender's secret domains cross as origin and path only, with no title, activity, presence, field values or pointers. Titles and activity lines have addresses cut to origin and path; typed values in activity are masked as they are locally; presence carries field and button names, never values. **Form values** cross host to joiner, and back only from a drive joiner: matched by frame and a stable key on the same page (origin and path) only, applied by setting the value and firing one "input" event (never "change", key presses or submit), never echoed back. Sensitive fields never carry a value: password type, card, one-time-code and password autocomplete, card, security-code, PIN, IBAN, SSN and similar names, and values that look like a card number (also inside other text), an IBAN, an SSN, a JWT or long token, or that contain a saved password. They cross as "filled" or "empty" only, and the other side shows an empty field with a "filled by" placeholder; a plain value both sides had that a card number replaced on one side is cleared on the other (never left stale or sent back), and a card number typed on one side is never overwritten from the other. Hidden and off-screen fields and file inputs are never read; frames on a secret domain give no values; at most 100 fields, 1000 characters per value and 6 frames per tab. **Tab order** is mirrored through the side panel extension's "tabs" permission (tab ids, positions and addresses), which only the helper asks over its private pipe. **Pointers** are document positions only, never what is under them; they are drawn in a closed shadow root, hidden from screen readers, and take no clicks; a watch joiner's pointer shows but pauses nobody. **Where each person reads** (the top and height of their viewport after their own scrolling, never an agent's) crosses the same way, as a small named mark on the right edge of the other side's copy. **Agent turns** cross too: an agent's label, color and how long its turn in a tab still holds; while another computer's agent holds a tab, agents here wait briefly or hear "in use", and never act in their copy. **Who is doing what** (agent label, color, tab address, status and task, last action) is redacted like messages, with addresses cut to origin and path, local ones not named, JWTs masked, and no last action from a tab that doesn't cross or crosses as its address only; activity lines cross the same way; prompts are never shared. **Messages** are text only (500 characters, 10 a minute), redacted (saved passwords become their names; card numbers, IBANs and SSNs masked), with no attachments. Watch joiners now send pointer positions and text messages, still no input. Only an approved drive joiner's changes reach your browser: another address for a tab they know, a new tab (opened from a shared one, or in the window of shared tabs; tabs in the joiner's other windows never cross), closing or moving one, field values, a person or agent at work in one; each is checked again here (the same address and field rules, so never your local network), at most 20 per request and 3000 per minute. An update applied on one side is never sent back (changes count only once a tab settles, and only when they differ from the other side's), and a tab that keeps bouncing stops sending for a while; at most 40 tabs and 2048-character addresses cross. |
| Shared browser mode shows or does more than meant | A join code with mode "shared" (the default for new codes; "follow" keeps the old behaviour) lets an approved joiner work in **your** browser: they see your tabs live and, with a drive code, click, type, scroll, draw and upload in them, logged in as you are, on any site you're signed in to (as with a drive invite link). What leaves your computer is a live picture and the sound of the tab they're looking at, sent **peer to peer** (WebRTC, encrypted with DTLS-SRTP) to their PairBrowse; the join tunnel carries only the connection's setup, and only when no direct connection can be made does it carry JPEG pictures and their input instead. Your cookies, logins, saved passwords and remembered details never leave your computer, and revoking the code ends it at once. To find the direct route both browsers ask a public STUN server (Cloudflare's) for their own address, and each side sees the other's IP address, as in a video call. Tab capture is allowed only to PairBrowse's own extension (`--allowlisted-extension-id`), never to a page; the browser shows its usual "sharing this tab" mark. Their input is checked before it's replayed (places inside the tab, mouse, wheel, keys as single presses, pasted text up to 2000 characters); copy, cut and paste shortcuts never reach your page, so your clipboard is never read; watch codes send no input. Their input counts as theirs (presence, fields they typed in), so your agents wait for them as for a person here. A file dialog their click opens is shown on **their** computer and the files they pick are sent over into that field (50 MB each), never a dialog on your screen. Their own agent works in your browser as a participant (turns, presence, its name): what needs your OK is handed to a person (it can't approve anything for you), and it can't use your saved passwords, remembered details, sessions, invites or files on your computer (uploads only from files its side sent over, checked by its own upload rules first). The notes on its results never include your own agents' notes (join requests, downloads), each person's steps in a tab are named as theirs, and addresses in those notes carry no query string or fragment. Everything visible in the tab shows in the picture, including pages on sites with saved passwords; password fields show as dots, as on your screen. |
| A shared dev server reaches more than the people in the session | Nothing on your computer is shared until you click: **Share** in the side panel, or **Yes** to an agent's `share_port` question there (agents can only ask; the side panel takes real clicks only, and its requests reach the helper only with your live view key from that extension's origin). Each shared port gets its own Cloudflare Quick Tunnel to a small proxy on 127.0.0.1, never to the dev server itself, at most 3 at once. The proxy answers only its tunnel's host name (or its own loopback address) and lets a request through only with a joiner's own 256-bit key, as an HttpOnly cookie their PairBrowse sets for that address in its browser (never in a URL; they take keys only for `*.trycloudflare.com` addresses); a key works only while that joiner is in the session (leaving, a revoked or expired invite end it at once). Watch joiners' keys allow GET, HEAD, OPTIONS and WebSockets only. The dev server gets the key's cookie removed, Host, Origin and Referer of `localhost`, and no forwarding or Cloudflare headers; redirects to localhost and cookie domains are rewritten for the shared address. Shares end with `unshare_port`, the last join code, `revoke_all` and the helper. What a drive joiner does there reaches your dev server like your own visits do. |
| A join code points somewhere else | On the joiner's computer, the code is checked strictly (an https `*.trycloudflare.com` address or a host in their `joinHosts`, a well-formed key, a known role). Their helper alone talks to the tunnel, with plain requests; nothing listens on their side for it, and every address from the host is checked again before their browser opens it. |
| A page tricks Claude into typing your password into the page's own form | Each secret works only on the HTTPS domains you list for it (`NAME_DOMAINS`), checked against the real address of the current tab, and of the frame the field sits in, by the helper, not by Claude. Fast mode never fills a payment provider's card frame. Values are masked in everything Claude reads (a password that holds a shorter one, whole), including the snapshot files Claude is pointed to. Screenshots can't be masked, so none is sent while a saved password shows anywhere on the page. |
| A page tricks Claude into uploading private files | The browser reads files only from `~/.pairbrowse/files` and the project. `pairbrowse_upload` takes images, video, PDFs and office documents from anywhere, after the helper checks them, and copies them into `files/uploads` first; key, password and credential files (`.env`, `*.pem`, `id_*`, `credentials.json`, anything in `~/.ssh`, `~/.aws`, `~/.gnupg`, the Keychain or `~/.pairbrowse`) are always refused, also through a link or in another casing of the folder name, and so is any file whose contents hold a private key or a `SECRET=` style line, whatever its name. It won't click a submit, publish, pay or delete button to find a file chooser. Any other file type goes through `browser_file_upload`, which asks you. |
| A page tricks Claude into submitting, paying, deleting or messaging | Real commitments ask you first; ordinary steps don't. (In Claude Code's bypass-permissions mode, which you turn on yourself, nothing asks: the guard then allows what it would have asked about and keeps its refusals; the helper's own refusals stand in every mode.) The helper reads every click by what it does, from the page's structure only (no word lists, so any wording, any language and icon-only buttons are covered). Strong signals: card (`cc-*` autocomplete or a valid card number), IBAN (by checksum) or billing/shipping fields or a payment frame (`allow="payment"`) in the form, or a card field in any frame on the page, make a submit a payment; a danger-styled button (by its computed color), a submit in a confirmation dialog (`alertdialog`, or a dialog with a danger button), a DELETE method (`_method`, `data-method`, `htmx`) or the confirmation a delete or payment click just opened make it a delete or payment; an element it can't read counts as one too. Such a click is refused until Claude names that class at the start of the description ("Pay: Submit order", "Delete: OK"), which is what the hook asks you about; another class or "Safe:" changes nothing. Everything else goes without a refusal or a question: links, tabs, plain buttons, sign-in, search and GET forms, steps of a multi-step form, and ordinary form submits such as a sign-up step or a settings save. Claude or Codex names the final actions it knows of from its task ("Pay:", "Delete:", "Publish:", "Send:", "Submit:" for an application, a final order or a submit for review) and every named click asks you (a drag when either end is named); that naming depends on the agent: one that misreads a plain submit lets it go without asking. No other model or service judges a click; nothing about a click leaves the computer. "Publish:" clicks (submit for review, go live) are blocked until a passing review is recorded, then still ask. A page's own confirm dialogs are never answered OK by PairBrowse; Claude's OK on one right after a delete or payment click needs that class (and asks you), any other OK goes unless Claude names it ("Submit: OK" asks you). In Codex and other apps that can't ask, every named final action is refused and handed to you. Clicking by screenshot position (`pairbrowse_click_at`) refuses strong-signal buttons and anything inside a frame, pressing a key that would press such a button for you (Enter or Shift+Enter in a field, Enter or Space on a focused button or link, a line break in typed text) is refused, and fast mode stops at a click step whose element has a strong signal or that Claude names as a final action. |
| A page fakes the "Your turn" badge | The badge only answers to a random key generated each time the helper starts, which pages can't read. A page can still draw its own look-alike: Claude only ever asks you to solve CAPTCHAs, sign in or confirm, never to enter card details or codes into a badge. |
| Escaping the browser | No `file:`, `javascript:`, `chrome:` or `data:` navigation, from Claude or from the live view's address bar. The run-arbitrary-code tool is removed. Chromium runs with its own sandbox (pages and the GPU process walled off from your computer, as in your everyday Chrome); see Limits for where it's off. Local-network addresses (router, localhost) ask first (in Codex they're refused: open them yourself); a fast-mode `go` step to one is refused outright. |
| A page reads or leaks what Claude typed | The tool that runs scripts inside a page (`browser_evaluate`) isn't offered to Claude; a call to it anyway asks you (in Codex it's refused). Tools that let pages register their own commands for Claude (WebMCP) are turned off. |
| Supply chain | The browser runtime is installed from a lockfile with checksums, at exact versions, with install scripts disabled. On macOS, ungoogled-chromium is pinned by SHA-256 and checked for notarization. Native PairBrowse builds come from the project's GitHub release and go through an install step: the archive must match a SHA-256 (the pin in `scripts/native-pack.mjs` when it installs on start; the `.sha256` file you give it by hand), its build manifest must name this platform and chip, on macOS the app's signature must verify (ad hoc: that shows the files are intact, not who built them; Linux and Windows builds are unsigned, so the SHA-256 is their only integrity check), and a launch check must pass, or the previous build comes back (also after an install or rebranding that was cut short: the next install or start puts it back). The engine pack the native browser launches with is code the helper loads: its archive must match its pinned SHA-256, and each of its files is checked against its own pinned SHA-256 again every time before it's loaded. Each release's files are checked against those pins in GitHub Actions and the check is attested in Sigstore's public log (`gh attestation verify <file> -R pairbrowse/pairbrowse`); it proves the files are the pinned ones, not who built them or from what. Hooks and the helper use only Node's standard library. |
| A site floods or poisons your Downloads folder | Files a site hands over are saved to your Downloads folder like in any browser, under a plain file name the site can't use to reach other folders, never over an existing file. PairBrowse doesn't limit how many a site sends; Claude is told about each one. |
| A recording captures or leaks more than meant | `pairbrowse_record` and the side panel's Record button record only the PairBrowse browser's own tabs (the extension's tab capture, no screen or other apps, so no system permission), shown as the browser's capture indicator on the tab and a running timer in the side panel. The video is encoded inside the browser and handed to the helper over the browser's private pipe, never over the network; the side panel's button is an owner-only live view route that joiners' links can't reach. It is saved in your Downloads folder under a new name (never over an existing file), private to your user (0600). Pages look as they do on screen: password fields stay dots, but other text on screen is in the video, so share it as you would a screenshot. A recording stops at an hour (saved) and is lost if the browser closes. |
| Card numbers or codes show up on screen or in logs | The activity line, bottom bar, side panel and run log mask card numbers (any value that is one, whatever the field, also inside other text) and card, security-code, PIN, IBAN, SSN and similar fields. A value typed into a field that is sensitive by its own kind (password type, card or one-time-code autocomplete, card, code, PIN and similar names) is masked even when Claude names the field only by its reference. Screenshots Claude gets show the page as it is, card fields included. |
| Another participant's message tries to steer your agent | Messages from other agents or a joiner reach your agent marked as coordination information from another participant, not an instruction from you, that authorizes nothing. They never confirm pay, publish, delete, send or submit clicks, never skip the safety hook, a confirmation or a review, and never lead to typing secrets, uploading files, opening local-network addresses or approving joiners: your agent acts only on your requests. Text only, 500 characters, 10 a minute, redacted, no attachments. |
| An agent overrides people, or resumes itself | "Pause agents" and "Resume" come from people only: the page's bottom bar (its "Pause agents" button, in a closed shadow root; a real click; Pause counts even during an agent's action, Resume only outside one, and neither is ever input in the page), the side panel and drive viewers of the live view (with its key), and drive joiners' helpers; a watcher's is refused. No tool pauses or resumes, and messages can't. A paused agent's call does nothing and answers after a minute. A person clicking or typing in a tab (here or in a drive joiner's copy) pauses the agents in that tab until they've stopped for two seconds, also during an agent's action (a press away from what the agent acts on, or keys while it doesn't type, are the person's; a drawing stroke under way stops at once, a fast-mode fill waits before its next field); moving the pointer and scrolling pause nobody. A field a person filled stays theirs for 5 seconds after their last keystroke (10 while they stay in it), and a text field's "change" on leaving it never counts as typing: an agent's typing, filling, choosing or ticking there is refused unchanged; across browsers only the filler's name travels with the field, never more. |
| A web page picks a session or joins one for you | The session picker (at start, or opened again from the side panel's **Switch session…**, which only you can press) is the side panel extension's own page, which web pages can't open, frame or script (it has no web-accessible resources). It reaches the helper only through the live view, with your key, which it reads from the side panel's memory, and the live view takes its requests only from that extension's origin (or loopback with the key); a page has neither. Choices count only from real clicks and key presses. A join code is only ever what you typed or pasted there, never filled in from anywhere, and goes through the same checks as `pairbrowse_join`; the host still has to let you in. Once a session is chosen, the picker takes no more choices. To show who used each session, the helper keeps names, apps and the kind of computer (Mac, Linux or Windows, never the computer's own name) in `~/.pairbrowse`, nothing about what they did; a joiner's PairBrowse sends its kind of computer with its join request. |
| Files at rest | Everything in `~/.pairbrowse` is created private to your user (`umask 077`), including saved tab lists. Each session is a Chrome profile separate from your everyday Chrome. |
| The safety hook fails, or doesn't run | It asks you instead of allowing. The helper enforces the secret, navigation and code rules on its own, whatever the permission mode, and everything the hook would block (blocked tools, `file:` and similar addresses, a publish without a passing review) stays blocked even with hooks off or the server added without the plugin. |
| Another app drives the browser (Codex, any MCP client) | Those apps can't be relied on to run the safety hook or ask you (Codex treats a hook's "ask" as a failure and goes ahead), so the helper applies the hook's rules itself for every app other than Claude Code: what Claude Code would block stays blocked, and what it would ask you about is refused with a note to hand it to you. |

Limits, honestly:

- Anything running as your user can read files in your home folder, including this Chrome
  profile. PairBrowse can't protect against malware already on your computer.
- The click guard reads a click by what it does, from the page's structure (payment fields and
  frames, danger styling, delete methods, confirmation dialogs), plus the final actions Claude
  names from its task. It catches mistakes and injected instructions, not every possible trick: a
  plain-looking button that commits to something, on a page with none of those signals, goes
  through unless Claude names it. Read what a confirmation prompt says.
- Prompt injection can't be fully solved. Watch the browser (or the live view) on sites you don't trust.
- An invite link shows everything on screen in your logged-in browser, and a drive link lets
  that person click and type in it as you, on any site you're signed in to. Share links only
  with people you trust, over a private route (your tailnet or SSH), and revoke them when done.
  Claude makes watch links without asking, so a page that tricks Claude could get one made;
  it's only reachable over your private route.
- Chrome's own sandbox is on by default (macOS, and Linux as a regular user). It's off when you set
  `"chromeSandbox": false`, when PairBrowse runs as root on Linux (Chromium refuses it there), and
  where the system can't run it (no user namespaces: a container such as Docker with its default
  seccomp profile, or Ubuntu's AppArmor rule that restricts them, where Chromium would need a
  root-owned setuid helper): the browser then starts without it and the helper log says so once. Without it,
  a page that exploits a browser bug isn't contained the way it is in your everyday Chrome.
- PairBrowse doesn't solve CAPTCHAs or bot checks and won't integrate solving services.
- On macOS the browser is ungoogled-chromium, which has no Google Safe Browsing (no phishing or
  malware warnings), and its security updates come from that project, usually some days after
  Chrome's. PairBrowse pins one build by checksum and doesn't update it by itself.
- On a Linux machine without a screen, the browser runs headed on a private virtual screen
  (Xvfb) started without TCP and behind an X cookie kept in `~/.pairbrowse/run`, so other users on
  the machine can't watch it or send it input.
- On Windows, the socket is a named pipe with Windows' default permissions, and the
  file-permission checks are skipped.

Report security issues privately; see [SECURITY.md](../SECURITY.md).
