# Security

PairBrowse drives a browser that is logged into your accounts, so it's built to keep that
browser to you and to Claude, and to limit what a malicious web page can talk Claude into.
Each row of the table ends with the tests that keep it true (`test/security-table.test.mjs`
checks that every row names tests and that they exist).

| Risk | What PairBrowse does |
|------|----------------------|
| Another program or user on your computer takes over the logged-in browser | No remote-debugging port. The browser is driven over a private pipe by the PairBrowse helper, and the only way in is a socket file in `~/.pairbrowse/run` that only your user account can open. Multiple trusted Claude Code sessions share a serialized queue and control leases; a call that holds the queue for more than 10 minutes is answered with an error and the browser is reset, so one stuck call can't keep every other session waiting. Tests: `test/collaboration.test.mjs`, `test/security.test.mjs`, `test/integration/turn-cap.test.mjs`. |
| A server's virtual screen is watched or driven by another user | On a Linux machine without a screen (or with `display` `"xvfb"`), the browser runs headed on a private virtual screen (Xvfb) that PairBrowse starts itself: no TCP (`-nolisten tcp`), behind a random X cookie kept in `~/.pairbrowse/run` (a folder only your account can open), so other users on the machine can't watch it or send it input. A display is used only once PairBrowse's own Xvfb still runs and holds the display's lock, so the browser never lands on an X server another program started on the same number at the same moment. Each screen leaves an ownership record beside its cookie (`run/<cookie name>.json`: display, pid, cookie path, size, start time; owner-only), and cleaning up goes by that record, never by a guess: at the next start, the recorded Xvfb is ended only if that pid still runs as your user with Xvfb's own command line behind PairBrowse's cookie, and the recorded display's lock (and its socket) is removed only if it holds that pid, the pid is gone and the files are your user's. Any other X server, lock, socket or process is left alone. Xvfb is ended and the cookie deleted whenever the helper stops (SIGTERM, then SIGKILL after 1 s), and the record is deleted once Xvfb has exited; one still running 1 s after SIGKILL keeps its record, and so does an Xvfb the next start can't end, so the following start tries again and clears the lock and socket a killed Xvfb leaves; at an abrupt exit it is told to end at once and the cookie deleted, and what is left is ended by that record at the next start. An Xvfb that exits by itself has its cookie deleted at once and its record kept for the next start's cleanup, and the browser on it is closed; the next action starts a new screen. An Xvfb left by a version from before the record is left alone. Tests: `test/display.test.mjs`, `test/supervise.test.mjs`, `test/security.test.mjs`. |
| A switch in `config.json`'s `browserArgs` opens a debugging port or weakens the browser | The user's own `browserArgs` (or, while that is unset, the older `chromeArgs`) are screened before launch against an allowlist (`scripts/browser-args.mjs` `ALLOWED`, listed in [configuration.md](configuration.md)): language, window, scale, colors and fonts, GPU and display backend, sound, notifications, quieter starts, `--enable-features` (feature names only), `--host-resolver-rules` that map names to this computer's loopback only, each passed only with a value of the shape it takes. Every other switch is dropped in any spelling the browser reads (`--x`, `-x`, `/x` on Windows, any case on Windows), whatever its value: a remote debugging port, address or pipe, `--remote-allow-origins`, switches that run another program as part of the browser (`--renderer-cmd-prefix`, `--utility-cmd-prefix`, `--gpu-launcher`, `--browser-subprocess-path`), `--disable-web-security`, `--disable-features` (site isolation off), `--ignore-certificate-errors`, `--allow-file-access-from-files`, `--unsafely-treat-insecure-origin-as-secure`, a proxy, `--auto-open-devtools-for-tabs`, another `--user-data-dir`, `--load-extension`, `--disable-extensions-except`, `--allowlisted-extension-id` and any switch PairBrowse doesn't know. Every item that isn't a switch (the browser would open it as a page or file; a value written as the next item is one) and everything after a bare `--` are dropped too. One helper log line and a warning in `pairbrowse_status` name each dropped switch (an item that isn't a switch is only counted). The few switches only the test suite needs (`--headless`, so a person's browser always shows its window and no measurement comes from a headless run; `--use-mock-keychain`, `--password-store=basic`, `--disable-features=LocalNetworkAccessChecks`, which loosen the browser) pass only in a helper the test harness started; elsewhere they are dropped and named like any other (`scripts/testenv.mjs` `harnessStarted`). The driver's own pipe and profile and the side panel's own extension switches are added apart from them and stay. `--no-sandbox` in any spelling is the sandbox choice, never a raw switch: on Linux the documented opt-out (it reaches the driver as its sandbox option), on macOS and Windows refused (see the sandbox row). The native browser's `pairbrowse` block in `config.json` can't go around this: only PairBrowse's own settings and the engine's fingerprint options (`scripts/config-schema.mjs` `PAIRBROWSE_ENGINE_KEYS`) reach a launch; any other key there (`extensions`, a proxy, launch options, switches) is named as unknown in `pairbrowse_status`, left out and logged. The same holds for a saved profile (`pairbrowse.profile`) and the persona kept with a session (`pairbrowse-persona.json`): only the engine's fingerprint options pass from them, and every other option (launch arguments, environment, ignored default switches, the sandbox, the executable, extensions, agent and storage options) is named in one helper log line per layer (names only, never values) and dropped (`scripts/native-engine.mjs` `readSettings`), so the only extension any launch loads is PairBrowse's own side panel. A proxy in a saved profile (`pairbrowse.profile`) or in the persona kept with a session stops the launch with an error saying to move it to `config.json`'s `network.proxies` (it is never dropped, which would turn a proxied session direct), and a proxy a launch is given with a username, a password or user info in its address is refused before the engine pack sees it, so credentials never reach the driver's proxy option (which would answer any site's 401 with them) or a switch; they will reach the browser only through a build's owner-only proxy auth file (manifest `proxyAuthFile`), and the open build never takes them (`scripts/native-engine.mjs` `personaProxyRefusal`, `proxyCredentials`; `scripts/browser/choice.mjs` `shellFrom`). A session's proxy comes only from `config.json`'s `network` (`scripts/net/config.mjs` `launchPart`, `scripts/daemon/network.mjs` `forLaunch`): the helper passes it to the driver itself with this computer's loopback addresses always around it, and in strict mode (the default; for SOCKS5 always) adds its own `--host-resolver-rules` (no name looked up except the proxy's and `localhost`) after the driver's and drops a user's, and in strict mode `--webrtc-ip-handling-policy=disable_non_proxied_udp` on both builds, plus on the open build `--force-webrtc-ip-handling-policy=disable_non_proxied_udp`, the spelling its browser reads (without it the browser still gathers this computer's public address through STUN); a proxy's username and password go only into an owner-only auth file (0600, fresh name under `run/`, deleted once the browser is up or its launch failed) named by a switch, on a build that declares `proxyAuthFile`, and anywhere else the session is refused; a network that can't be used refuses the launch, never a direct start. (Extensions the person installs from the Chrome Web Store in a PairBrowse browser build that supports it load as in any browser: see the Web Store row.) Tests: `test/browser-args.test.mjs`, `test/fuzz/browser-args.test.js`, `test/config-schema.test.mjs`, `test/native-engine.test.mjs`, `test/browser-choice.test.mjs`, `test/net-launch.test.mjs`, `test/net-credentials.test.mjs`. |
| The live view is reached by someone else | Starts with the browser, for its side panel. Listens on 127.0.0.1 only, on a random port (or your `liveViewPort`), behind a random 256-bit key in the URL. Join codes use a second 127.0.0.1 port (the only one the sharing tunnel reaches), where your key never works. Requests for any other host name are refused (stops DNS-rebinding), except the names you list in `liveViewHosts`, which take invite and hand-off links only; input posted from other websites is refused too. The page sends no referrer, can't be framed, and runs only its own script and style files (a strict content security policy: no inline code or styles, nothing loaded from the web); those files come from a fixed list read at start, behind the same key. It stops when the browser closes. The side panel gets the address in memory at launch (extension session storage, never on disk), and the extension's own pages (the session picker and the settings page, which web pages can't open, frame or script: no web-accessible resources) read it from there; the settings page reads the owner's event stream through the one shared stream (below), with no page stream and uses only the config, profile, joinhost, invites, invite, timeline, tabs, diagnostics and report routes with your key, so passwords never reach it as values; the live view accepts its posts only from that extension's origin or loopback, still with the key (with a build that has its own pages, those pages use a second key: see below). Join requests (`joins.json`), approvals waiting for an answer (`approvals.json`) and answering either (`approve`) are owner-only: your key or the browser's own pages' key; invite links get 403 and the join-code port never serves them. Tests: `test/liveview.test.mjs`, `test/fuzz/security.test.js`, `test/invites.test.mjs`. |
| An invite link goes further than meant | Each invite has its own random 256-bit key, separate from yours, checked in constant time, and ends after 24 hours (7 days at most), when you revoke it, or (an invite link) when PairBrowse stops or you close the browser window; a join code is kept across a restart of PairBrowse until it expires, you revoke it or you close the browser window (see "A join code goes further than meant"); expired and revoked keys get the same answer as a wrong one, and an open view ends at once. A watch link gets the page, tabs, activity and status only: the helper refuses its clicks, typing and tab changes. A drive link can also click, type and switch tabs, and only after you OK it (in Codex and other apps, Claude can't make one). The approve role (a shared browser join code only, never a link or a follow code) is a drive invite that may also answer your approval cards (see "A joiner answers your approval cards"); making one, or switching an invite to it later (`pairbrowse_invite set_role`), asks you first in the same way, and the Share card's third choice and Settings' "Can approve" take your own click. Neither ever gets the Profile panel (remembered details, password names) or its updates, and a drive link can't open local-network addresses from the address bar. Drive input is accepted only from loopback or your `inviteBaseUrl` origin, and every event is checked before it is replayed, as a joiner's is: known kinds only, places inside the picture, modifiers as single keys, text cut to 2,000 characters, the named keys and the select-all, undo and redo commands only (never another letter shortcut or Insert), no cut command and no Shift+Delete (so nothing a drive link sends reads or writes your clipboard), and at most 600 events at once, then 200 a second, per invite; a body that isn't JSON is a 400 on every route that parses one. Viewers other than you can't resize the page. Anyone with a drive link can still click and type in your logged-in browser. Tests: `test/invites.test.mjs`, `test/fuzz/joiner-input.test.js`. |
| The live view's timeline shows more than the goal log | The Timeline in the live view's right panel reads GET journal.json with your own key only; invite links and join codes are refused (403), and the join-code port never serves it. It returns the current run file as the goal log wrote it (page titles and addresses, each cut to its origin and path with no query or fragment, the bottom bar's one-line descriptions, hand-off texts, the names of fields a fast-mode run left empty, the time it was saved), with saved passwords masked again on read, since an agent's run_save can take the file over. Read once when the Timeline opens and when you press Refresh, never polled; no picture, no field value, nothing new is captured or kept for it. Tests: `test/liveview.test.mjs`, `test/redaction.test.mjs`. |
| The Share card makes an invite without you asking | The Share button in the side panel header and the live view toolbar (your own link only) posts to POST invite on the owner's port with your own key, under the same host, origin and key checks as every POST; invite links get 403 and the join-code port never serves it. It makes only the card's three choices (a join code that can drive in the shared browser, the same code that can also approve, or a watch link) by running the same code as `pairbrowse_invite` create, with your click as the OK a drive or approve invite needs (the card ignores a synthetic click), and asks your first name once, as create does. The code or link is returned only in that answer and shown once in the card (cleared when it closes); it is never written to the log, state.json or the event stream. Besides `pairbrowse_invite` revoke / revoke_all, PairBrowse's Settings lists the invites out now and revokes one: `GET invites.json` answers `{ items: [{ id, role, label, share, mode, expires }] }` (never a key, code or link), `POST invite { op: "role", id, role }` ("drive" or "approve", a shared browser join code only: Settings' "Can approve", your own click) switches its role, and `POST invite { op: "revoke", id }` (an 8-hex id, nothing else in the body; at most 2,000 characters) ends that invite at once exactly as `pairbrowse_invite` revoke does (anyone using it is out, an open view ends, a join code's tunnel goes with the last code). Both take your own key or the browser's own pages' key only: invite links get 403 and the join-code port never serves them; no agent tool reaches them. Your own streams hear an `invites` event (the same list, never a key) when one is made, revoked or expires. Tests: `test/share.test.mjs`, `test/h3-routes.test.mjs`, `test/ui-strip.test.mjs`. |
| The browser's own pages reach the helper, or something else reaches them | Only with a native PairBrowse build whose manifest declares its own pages (today's builds don't: then the side panel loads as before and none of this applies). The helper launches such a build with two switches: `--pairbrowse-helper=<the live view's 127.0.0.1 origin>` (the address alone, no secret) and `--pairbrowse-helper-key-file=<path>` (a build with a capture page gets a third, `--pairbrowse-capture-key-file`, for that page's own key, kept the same way: see the capture page row). The key is a second 256-bit key with your rights, minted with the live view, separate from the key in your live view link, and it never rides the command line: the helper writes it, alone, into a new file under `~/.pairbrowse/run` (a folder only your account can open) with a fresh random name at each browser start, readable only by your account (mode 0600 on macOS and Linux; the browser refuses the file if group or others could read it), and passes only the file's path, so `ps`, `/proc/<pid>/cmdline`, `chrome://version` (which a shared tab could stream to guests) and crash dumps show a path, never the key. The browser reads the file once and keeps the key in memory; the helper deletes the file on the first request one of those pages makes with that key, and in any case when the browser closes, when its launch fails and when the helper stops; a file left by a helper that was killed is deleted at the next browser start. Neither the key nor the file's path is written to the log, state.json, the event stream, the saved sharing state or any tool result (`pairbrowse_liveview` shows your link's key, never this one); the key is gone with the live view when the browser closes. The browser hands the origin and key only to its own `chrome://pairbrowse` pages, never to a web page or an extension. In a build whose manifest declares its settings section (`settingsSection`; the helper reads it with the build's other fields and tells its own pages only that boolean, in `config.json`), those pages may be framed only by the engine's settings page (`chrome://settings`, shown as `pairbrowse://settings`), whose PairBrowse section (`chrome://settings/pairbrowse`, shown as `pairbrowse://settings/pairbrowse`) frames PairBrowse's own settings page; of framed pages only that settings page, framed directly by a tab's `chrome://settings` main frame, gets the origin and key, and `chrome://settings` itself never does (it cannot read the cross-origin frame either). The framed settings page sends its parent one message, its height (`{ type: "pairbrowse-settings-height", height }`, to `chrome://settings` only), and the section takes it only from that frame and its origin. The old own settings address (`chrome://pairbrowse/settings`) opened as a tab goes to that section (the browser redirects it, and the page sends itself there if it ever loads as a whole tab and the helper says the build has the section). An older build, without the section, frames none of these pages (only the switcher, below): Settings is the tab page `chrome://pairbrowse/settings` itself, and the pages open it there. Tests: `test/ui-settings.test.mjs` (framed settings), `test/vocab.test.mjs`, `test/browser-choice.test.mjs`. The live view takes those pages' requests only from the origins `chrome://pairbrowse` and `chrome://pairbrowse.top-chrome`, allowed only in that mode, and opens CORS for those two origins alone (never `*`, never a web or extension origin), on your own port only, with your own key or theirs; the join-code port never answers them. In that mode no extension is loaded and no theme or new-tab override is set. Tests: `test/browser.test.mjs`, `test/liveview.test.mjs`, `test/context-picker.test.mjs`. |
| The PairBrowse browser you open yourself (the Dock, Finder, Spotlight, a login item) is driven by something else, or never by the helper | A browser started without the helper can't be reached by it later (the helper drives only a browser it launched, over that launch's pipe), so the PairBrowse browser on macOS and Linux (from the build with its native fixes, 555; an older build, or the open build, leaves a browser you open yourself a plain window no helper drives or reaches, and an agent opens its own) hands a bare start to the helper instead of opening a window. It reads `~/.pairbrowse/run/opener.json`, which the helper rewrites at each start with two absolute paths, the Node it runs on and its own copy's `scripts/open.mjs` (plus the helper's `home` and `instance`, which the browser ignores), and runs that Node with that script, nothing else, waiting at most 15 s (a run past that is ended); on macOS the opener disclaims responsibility for what it starts, so a helper it starts never inherits the PairBrowse app's camera, microphone, screen or folder grants (the helper's own identity in privacy prompts: the PairBrowse Agent row below). The PairBrowse browser, however it was started (by the helper, a terminal, the Dock), is its own responsible process (started by a program, it runs itself again in place, same process and pipe, before anything else), so its own prompts name PairBrowse. It takes the record only as your account wrote it: the file and its folder owner-only (0600 in 0700) and yours, at most 4 KB, version 1, no `..`, the script named `open.mjs` inside a `scripts` folder, both paths regular files owned by you or root and not writable by group or others. It looks for the record only on a start with nothing on the command line (no profile folder, no address, no driver or helper switch) that carries no link or document either (one opened from another app or the Finder is never handed over), before the profile or any window opens, so a browser the helper launched never runs it; `PAIRBROWSE_NO_OPENER` in the environment turns it off. (A development build also counts a start with only the two Keychain test switches as bare; release builds count every switch.) The opener only asks the helper, over its private socket (one line, the hooks' kind; no new port, socket or file), to open its browser, starting the helper as the agents' bridge does when it isn't running; the helper launches the browser exactly as for an agent (its own pipe, profile and persona, no remote-debugging port) or brings its open window forward, and the bare start ends without a window once the opener says yes. No record, a refused one, no yes within 15 s, or a helper set to another browser: the browser opens as a plain window, as before. Nothing makes a running browser drivable: an agent that starts later uses the window the helper opened, and a window opened without the helper stays out of its reach. Tests: `test/opener.test.mjs`. |
| With several PairBrowse helpers on one computer (named instances, another `PAIRBROWSE_HOME`), a PairBrowse browser you open yourself reaches the wrong helper | Besides `opener.json` (the default home's helper), each helper on macOS writes the record of the native build it launches into `~/.pairbrowse/run/openers/<bundle id>.json` (the bundle id from that build's `PairBrowse-build.json`: `app.pairbrowse.browser`, or `app.pairbrowse.browser.dev` for a development build; a name of letters, digits, dots and dashes, never a path), once its socket listens and after each launch, with the same form and checks as `opener.json` (0600 in a 0700 folder, written through a temp file and a rename) plus the helper's `home` and `instance`, which the browser ignores. The browser reads its own app's record first; when that record is there it decides. A helper never overwrites another helper's record while that helper answers on its socket, and removes its own when it stops cleanly. `scripts/open.mjs` uses a record's home only when the record belongs to the app that ran it (its parent process's bundle), names this very copy of `open.mjs`, and, for an instance, names that instance's own folder; otherwise it goes to the default home's helper, as before. A helper the test harness started keeps its records in its own home. Tests: `test/opener-registry.test.mjs`, `test/fuzz/records.test.js`. |
| A plugin update closes the browser under someone, or a line on the socket stops the helper whenever it likes | After an update the helper already running is the old copy. Each new bridge of the installed plugin (its folder inside Claude Code's plugin cache, `~/.claude/plugins/cache` or `$CLAUDE_CONFIG_DIR/plugins/cache`, or Codex's, `~/.codex/plugins/cache` or `$CODEX_HOME/plugins/cache`, compared as real paths, case-insensitively on macOS and Windows) first says its own version on the private socket (one line of the hooks' kind: `{"pairbrowse":"hook","op":"version","v":1,"version":"x.y.z"}`; the helper reads a line of up to 512 characters as this request, a longer one as none, and drops any single line over 64 KiB; no new port, socket or file) and waits at most 1.5 s for an answer of at most 4096 bytes. A bridge run from anywhere else (a checkout, whose own `.mcp.json` starts one, or a plugin loaded from a folder) never asks: its daemon.mjs never takes over the installed helper. The helper stops only when that version is a plain release version (`x.y.z`, at most 32 characters, no prerelease or build part) strictly newer than its own, and only while nobody and nothing uses it: no agent connected, no joiner or invite-link viewer in the live view and nobody in a shared browser session, not joined to another session, no recording running, no approval waiting, no download in progress (one started over an hour ago no longer counts), the browser not starting (launching, reopening its saved tabs, or switching sessions), the session picker not showing, `server.keepAlive` off (a helper the service manager keeps running on a server is never stopped this way), and no person's use of the browser for the last 2 minutes: input in a page (clicks, keys, the pointer, scrolling), the browser opened by hand, a pick in the session picker, one of the browser's own pages opened (its Settings, Downloads, History) or a press in them, the side panel or the live view's controls. Then it answers `{"restart":true}` and stops the way it stops on SIGTERM (the browser closed cleanly, so cookies are written and the open tabs saved for the next start), and the bridge waits up to 15 s for its socket and lock to be gone before it starts the helper from its own copy. While saved tabs are reopening nothing writes the saved list (a stop or a crash then leaves it whole, never the few tabs open so far); a stop waits up to 3 s for the restore to finish and saves the tabs once it has, all inside the stop's 5 s with at least 1.5 s left for the browser's own close (the save writes every tab by then, with the titles it could read). After starting a helper the bridge says its version once more (the helper that answers may be another bridge's that won the lock, perhaps an older copy; its own answers "same version"), at most two rounds, so the helper ends on the newest copy or stays in use and says a newer one waits; on macOS, PairBrowse Agent ending because another live helper holds the lock is not read as a refusal (no second helper on Node). Otherwise the answer is `{"restart":false,"why":...}`, the helper keeps running, and `pairbrowse_status` says that the newer version is installed and the browser moves to it the next time a session starts while nobody uses it (with `server.keepAlive` on: that only a restart of the PairBrowse service moves to it, since such a helper never hands over by itself); it never restarts later on a timer. An equal or older version, a malformed line or another version of the request changes nothing. An older helper doesn't know the request (it answers as a hook request it can't serve, or not at all), and the bridge then connects to it as before. Anything that can open the socket could already connect as an agent and drive the browser; this adds only a stop of an idle helper in favour of a strictly newer version string. Tests: `test/handoff.test.mjs`, `test/handoff-context.test.mjs`, `test/supervise.test.mjs`, `test/tabs.test.mjs`, `test/presence.test.mjs`, `test/liveview.test.mjs`, `test/bridge.test.mjs`, `test/integration/handoff.test.mjs`. |
| A project picks which PairBrowse profile the agent uses | The helper's home (its profile, logins, config, secrets, facts, runs) is `PAIRBROWSE_HOME` when set (not by the project: see the next row), else `PAIRBROWSE_INSTANCE`, else the `"instance"` in a `.pairbrowse.json` in the folder Claude Code runs in (`CLAUDE_PROJECT_DIR`, else the current folder; never a parent folder), else `~/.pairbrowse` (`scripts/home.mjs`). The file is read only when it is a regular file (a link isn't followed), owned by your account and at most 4 KB; the name is 1 to 32 of `a-z`, `0-9` and `-` and only ever selects `~/.pairbrowse/instances/<name>`, so a project can choose among your own instances (or start an empty one), never a folder of its choosing; a file that doesn't qualify is ignored and `pairbrowse_status` says so, and a malformed `PAIRBROWSE_INSTANCE` stops the helper, the bridge and every hook instead of falling back: one line saying what to fix and exit code 2, which blocks the call in PreToolUse (`scripts/paths.mjs`). `pairbrowse_status` names the instance and its home when it isn't the default, and the browser's docks show the instance. Instances share one read-only install of the runtime, browser apps, engine pack and cloudflared in `~/.pairbrowse`, each checked as before and installed one at a time under a lock there (`scripts/install-lock.mjs`: the lock names its holder by pid, the time that process started and a token of its own; a lock whose process is gone or started at another time, as with a pid used again after a reboot, is taken over, and a helper removes the lock only while it is still its own). Tests: `test/instances.test.mjs`, `test/install-lock.test.mjs`. |
| The helper uses the PairBrowse browser's macOS privacy grants, or its prompts name Node or the app that started it | On macOS a PairBrowse build carries PairBrowse Agent (`PairBrowse.app/Contents/Helpers/PairBrowse Agent.app`, bundle id `app.pairbrowse.agent`, signed with the build), and the helper starts on it whenever the browser it uses, or the one installed under `~/.pairbrowse/browser`, carries it (`scripts/launcher/daemon-connect.mjs`, both ways the helper starts: an agent's bridge and the browser's opener). The agent takes exactly two arguments, an absolute Node and an absolute `.../scripts/daemon.mjs` (anything else: it exits without running anything), runs itself again in place once with responsibility disclaimed (same process, arguments and environment), then runs that Node with that script as its child, passes SIGTERM, SIGINT and SIGHUP on and ends as the helper does. macOS then charges a privacy request the helper makes (the Downloads folder when it saves a file a site hands over, say) to PairBrowse Agent, an identity of its own: the prompt names PairBrowse ("PairBrowse Agent"), a choice made there holds for that identity alone, and the helper never uses what you granted the PairBrowse browser (camera, microphone, screen recording), Node, your terminal or the Claude app. Its Info.plist says why it may ask for the Downloads, Documents and Desktop folders and names no camera, microphone or Automation use (the helper makes none). Without it (another platform, no PairBrowse build, an older build, or an agent that ends before the helper listens: then once on Node) the helper runs on Node as before, charged to whatever started it. The browser the helper launches answers for itself either way (the row above). Tests: `test/daemon-connect.test.mjs`. |

Limits, honestly:

- Anything running as your user can read files in your home folder, including this browser
  profile. PairBrowse can't protect against malware already on your computer.
- The click guard reads a click by what it does, from the page's structure (payment fields and
  frames, danger styling, delete methods, confirmation dialogs), plus the final actions Claude
  names from its task. It catches mistakes and injected instructions, not every possible trick: a
  plain-looking button that commits to something, on a page with none of those signals, goes
  through unless Claude names it. Read what a confirmation prompt says.
- Prompt injection can't be fully solved. Watch the browser (or the live view) on sites you don't trust.
- An invite link shows everything on screen in your logged-in browser, and a drive link lets
  that person click and type in it as you, on any site you're signed in to. Share links only
  with people you trust, over a private route (your tailnet or SSH), and revoke them when done.
  Claude makes watch links without asking, so a page that tricks Claude could get one made;
  it's only reachable over your private route. A hand-off link (a grant, sent to your own
  channels when hand-offs are on: on a server or with Away) is a short-lived drive link for one
  tab: it opens once, for that tab only, until the hand-off ends or expires (`grantMinutes`),
  and points at the live view's own address (your private route), never the join-code port.
  Anyone who reads the message before you can use it, so set up only channels only you read.
- The browser's own sandbox is always on on macOS and Windows: `"browserSandbox": false` and `--no-sandbox`
  are refused there (named in `pairbrowse_status`), and a sandbox failure stops the launch with an error.
  On Linux it is on for a regular user, and off when you set `"browserSandbox": false` or
  `--no-sandbox`, when PairBrowse runs as root (the browser refuses it there), and where the system
  can't run it (no user namespaces: a container such as Docker with its default seccomp profile, or
  Ubuntu's AppArmor rule that restricts them, where the browser would need a root-owned setuid helper):
  the browser then starts without it, and the helper log, `pairbrowse_status` and the browser's bar
  say so. In server mode (PairBrowse's own virtual screen, or `server.keepAlive`) and with
  `"browserSandbox": "required"` none of that happens: off requests are refused, root and a system
  that can't run it refuse the launch, and the browser never starts without its sandbox. With the
  sandbox off, a page that exploits a browser bug isn't contained the way it is in your everyday
  browser.
- PairBrowse doesn't solve CAPTCHAs or bot checks and won't integrate solving services.
- On macOS the open build is a pinned open-source build without Google Safe Browsing (no phishing or
  malware warnings), and its security updates come from its open-source project, usually some days
  after the engine's own releases. PairBrowse pins one build by checksum and doesn't update it by itself.
- On Windows, the socket is a named pipe with Windows' default permissions, and the
  file-permission checks are skipped.

Report security issues privately; see [SECURITY.md](../SECURITY.md).
